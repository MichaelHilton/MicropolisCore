## Reading the table

This inventory contains **139 entries**: 9 menu entries, 111 button entries, 2 picker entries, 6 picker option entries, 11 toggle entries. It expands generated controls into individual rows: 16 city tools, 8 scenarios, 24 currently bundled sample cities, 4 terrain brushes, 6 graph series, and all budget arrows.

Shared System/Options/Disasters/Windows actions appear in both the native menu bar and the in-window menus and occupy one logical row each. Classic and Retro tool implementations are paired in the same row. The native application-menu About declaration is listed separately. Visibility depends on the current window, edit mode, appearance, and open menus.

The table includes menus, toggles, and picker choices alongside buttons so their clickable actions can also be used as a testing checklist. An em dash in the identifier or keys column means no explicit identifier or keyboard shortcut is declared for that entry.

Classic city tools are icon buttons: their first listed name comes from ToolSpec/help text; the second is the Retro caption. Tool letters such as Q and R are tooltip hints in the current code; the palette buttons do not declare keyboard shortcuts for those letters. Selecting a tool is free; listed costs apply when that tool acts on the map and may have additional clearing costs.

Source links point to the reviewed workspace and line numbers; generated rows link to their defining template or specification. This is a source inventory rather than a claim that every action has automated test coverage.

### Keep it opt-in

The separate Xcode UI-test target, `MicropolisButtonInventoryUITests`, lives in `Tests/MicropolisButtonInventoryUITests`, with its own `MicropolisButtonInventory` scheme. Its System, Options, and Map test classes share `ButtonInventoryTestCase` and reuse the existing UI-test host. The suite is excluded from the normal UI scheme, SwiftPM test targets, default test scripts, and routine CI checks.

The dedicated runner, `scripts/run-button-inventory-tests.sh`, uses XcodeGen and the separate scheme. Run these commands from `apps/micropolis-mac`:

```sh
# Run all inventory tests explicitly.
bash scripts/run-button-inventory-tests.sh

# Compile without taking over the desktop.
bash scripts/run-button-inventory-tests.sh --build-only

# Run a single row while developing it.
bash scripts/run-button-inventory-tests.sh \
  -only-testing:MicropolisButtonInventoryUITests/MapButtonInventoryUITests/test_B078_SelectAndUseQuery
```

The runner checks row completeness, disables parallel desktop execution, retains a result bundle and failure screenshots, and returns a failing status when a row fails. Test names contain row IDs. Run it manually before releases or after broad interface changes, during an agreed period when the desktop can remain idle. Existing everyday test commands are unchanged.

### Acceptance contract

- **Independent cases:** launch a fresh app with fixed seed, known city, sufficient funds, explicit appearance, and isolated preferences/files. Stop background simulation except where progress is under test; advance deterministic fixtures by bounded steps. Tear down windows, sheets, popovers, temporary files, and the app even after a failed assertion. Never depend on another row's test.
- **Actual interactions:** drive the real app controls and native panels. For shared menu actions, exercise both the native menu and in-window menu where available. For paired Classic/Retro controls, exercise both appearances. Check each declared keyboard shortcut in addition to clicking; palette tooltip letters are not declared shortcuts. For hidden Cancel, exercise Escape instead of attempting an invisible click.
- **Meaningful assertions:** check selected/checked state plus the resulting city, map, funds, window, or panel behavior described in the row. Render assertions use small deterministic regions with fixed viewport/scale and reviewed appearance-specific references, not fragile whole-desktop screenshots. Independently prepared fixture expectations must not be computed by invoking the same action under test.
- **Fixture prerequisites:** add explicit UI-test-only startup fixtures for disaster prerequisites, budget year-end, histories/overlays, graphics-load failures, and won/lost outcomes. Add a read-only observation channel where a result is not otherwise observable, for example engine flags, simulation ticks, sprite state, selected tool, or audio events. It may expose results but must not replace the button's action. These helpers do not exist merely because they are specified here.
- **Stable control lookup:** reuse existing identifiers. Add identifiers where needed, or use scoped, unambiguous native labels for system controls. Wait for activation, hittability, and specific results with bounded waits; avoid fixed sleeps, blind coordinates, swallowed failures, or skipping difficult rows.
- **Contained side effects:** use scratch cities for Open/Save and verify round trips. Cancel Print after checking its panel/preview; do not submit a print job. Exit terminates only the launched test instance. Isolate or restore sound and appearance preferences. Reactivate the app after Hide.
- **Traceability:** require all 139 row IDs to map to distinct discoverable tests in the dedicated target. Keep parameter cases inside each named row test or report them under that row ID. A row is implemented only after its full behavior contract and applicable appearance/menu/shortcut cases run successfully; a lookup-only check does not satisfy it. Update this inventory and the mapping together when generated controls change.

## Scope notes and testing observations

- Sample-city rows follow the actual `Assets.allCities` generator: sorted bundled `.cty` files, excluding names beginning with `scenario_`. The 24-row expansion agrees with both the current resource bundle and content directory. Additional bundled cities create additional buttons at runtime. Scenario rows are expanded separately from `Scenario.allCases`.
- Appearance choices come from `GraphicsPackage.allCases`. The picker is available in Options and through the Retro HUD appearance menu. City/terrain palettes are shown according to edit mode, and Classic/Retro city palettes according to graphics selection.
- The Retro play/pause button, Speed picker/choices, application-menu About, alert OK buttons, Windows Close/Hide, and overlay submenu choices lack dedicated accessibility identifiers. The Retro appearance opener now has `menu.appearance`. The Appearance picker has a container identifier; its individual choices do not have identifiers. On the tested macOS version, SwiftUI replaces declared identifiers on generated nested scenario/sample actions with `menuAction:`; tests select their exact titles within the opened in-window menu.
- New City's Cancel button is explicitly hidden. Its cancel keyboard shortcut is declared in code; its presence in this inventory records the declaration rather than a visible button.
- EvaluationView contains presentation only. Demand bars, HUD text, DOSWindowTitle, and DOSButtonLabel are presentation elements rather than independently actionable buttons.
- Native window traffic lights, OS-generated menu items, and controls inside the system Open, Save, Print, and About panels are supplied by macOS. They vary with OS version and are outside the app-defined table. The app invokes them from [GameMenus.swift:15](/Users/michaelhilton/Development/AI-Projects/MicropolisCore/apps/micropolis-mac/Sources/MicropolisMac/Views/GameMenus.swift:15), [GameMenus.swift:29](/Users/michaelhilton/Development/AI-Projects/MicropolisCore/apps/micropolis-mac/Sources/MicropolisMac/Views/GameMenus.swift:29), [GameMenus.swift:38](/Users/michaelhilton/Development/AI-Projects/MicropolisCore/apps/micropolis-mac/Sources/MicropolisMac/Views/GameMenus.swift:38), and [GameMenus.swift:12](/Users/michaelhilton/Development/AI-Projects/MicropolisCore/apps/micropolis-mac/Sources/MicropolisMac/Views/GameMenus.swift:12).
- Map clicks, dragging, scrolling, pinch zoom, and overview-map navigation are gestures rather than buttons. They need separate interaction tests. Engine-only tool cases such as network, land and forest do not imply additional city-palette buttons; the terrain brushes are inventoried above.
